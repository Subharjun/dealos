# DealOS Marketplace site (Power Pages)

**As of:** 6 October 2026
**Site:** https://dealos-gigacore.powerappsportals.com (private to the gigacore tenant, Trial: expires about 4 January 2027)
**Source:** [portal/](../portal/), a React + Vite + TypeScript single-page app deployed as a Power Pages **code site**

Buyers and sellers use this site; staff use the admin app. The site never talks to the agents directly. It writes records (an RFQ, a listing, a chat message), and the flows and plug-ins already described in [WORKFLOWS.md](WORKFLOWS.md) and [AGENTS.md](AGENTS.md) take it from there.

## Pages

| Route | Who | What it does | Tables |
|---|---|---|---|
| `/` | Everyone | Catalog: search and filter published listings, each with badge, price, quantity, terms and evidence | `gc_catalogentry` |
| `/listing/:id` | Everyone | Listing detail: every market-visible value with its evidence status. Buyers invite the seller to quote against an open RFQ | `gc_catalogentry`, `gc_rfqinvite` |
| `/company` | Signed in | Onboarding: create the company (roles Buyer / Seller / Intermediary), then KYB status, trust tier and KYB document upload | `account`, `contact`, `gc_document` |
| `/sell` | Sellers | My listings, RFQ invites to accept or decline, matches to opt in to | `gc_listing`, `gc_rfqinvite`, `gc_match` |
| `/sell/new`, `/sell/:id` | Sellers | Create a draft listing. Detail: evidence, the verification team's open questions, document upload, submit, withdraw, delete draft | `gc_listing`, `gc_fact`, `gc_question`, `gc_document` |
| `/buy`, `/buy/new`, `/buy/:id` | Buyers | RFQs: create a draft, send it (Open starts matching), opt in to matches, track and withdraw invites | `gc_buyerrequirement`, `gc_match`, `gc_rfqinvite` |
| `/deals` | Both | Deals with stage track, overlay, offers; rate the counterparty after settlement; raise a dispute | `gc_deal`, `gc_offer`, `gc_rating`, `gc_dispute` |
| `/chat` | Both | Buyer Concierge or Seller Assistant chat | `gc_conversation`, `gc_message` |

## How data is protected

Three layers. Each one is enough to stop the obvious attack on its own.

| Layer | Where | What it does |
|---|---|---|
| **Masked catalog** | `gc_catalogentry`, built by the `CatalogPlugin` | The only listing data anonymous users and buyers can read. It has no seller, asset, listing title or exact location, and only Market Safe / Market Generalise facts with status Verified, Documented or Claimed. It is rebuilt when the listing, its facts or its lots change, and it is removed when the listing stops being Published. `gc_RefreshCatalog` rebuilds everything. |
| **Table permissions** | [portal/.powerpages-site/table-permissions](../portal/.powerpages-site/table-permissions), generated by [tools/portal_config.py](../tools/portal_config.py) | Rows a user can reach: their own contact, the company they created, their company's listings, RFQs, documents, deals and conversations, and the children of those through Parent scope. The Web API returns only the columns in `Webapi/<table>/fields`. Deals expose no buyer or seller lookup. |
| **Portal guard** | `PortalGuardPlugin`: synchronous pre-operation on every table the site writes, active only when `IsPortalsClientCall` | Knows the signed-in contact (`PortalsContactId`) and their company. It **forces ownership** (seller, buyer, uploader, conversation owner) and refuses columns staff own (badge, KYB status, trust tier, parse status and so on). It allows **only legal status changes**: a seller can submit or withdraw a listing but never publish it; a buyer can open or withdraw an RFQ; only the invited seller can accept an invite; each side can opt in only for itself; a chat message is always the user's, never the platform's. A company can be joined only by the contact who created it. |

The pure transition rules are in `PortalRules` and are unit-tested in the harness ("portal: …" checks).

**Known limits:**
- One contact per company: the creator is the account's primary contact. Adding colleagues needs staff for now.
- The site is private and sign-in uses the tenant's Microsoft Entra ID. External buyers and sellers need **Microsoft Entra External ID** configured as an identity provider before launch.
- Listing names written by sellers can appear in match notifications and match names; the site and the Seller Assistant generate names from commodity, grade and quantity to avoid this.
- Offers and counter-offers can't be sent from the site yet. They are read-only there, and the guard refuses offer writes from the site.

## Build and deploy

```bash
cd portal
npm install
npm run build                                   # tsc (strict) + vite → dist/
export DOTNET_ROOT=/opt/homebrew/opt/dotnet/libexec
~/.dotnet/tools/pac pages upload-code-site --rootPath .     # settings come from powerpages.config.json
```

- **Permissions changed?** Edit `PERMISSIONS` / `FIELDS` in [tools/portal_config.py](../tools/portal_config.py), run `python3 tools/portal_config.py`, then build and upload. The script rewrites only `DealOS-*` permission files and the `Webapi-*` settings.
- **New column used by the site?** Add it to `FIELDS`. A Web API 403 with `AttributePermissionIsMissing` means a column is missing there. Lookups need `_<column>_value` to read and the navigation property (for example `gc_Requirement`) to write.
- **Data model:** tables come from [tools/deploy_schema.py](../tools/deploy_schema.py); plug-ins and steps from [tools/deploy_agents.py](../tools/deploy_agents.py).
- **Prerequisites done once in Dev:** `js` removed from the environment's blocked attachments (code sites need it), and the site activated through the Power Pages API (website id `03a6c2cb-7e12-428b-9db4-606e93bc8ff0`, website record `880f6ff2-3212-4abd-b007-b79d3c9bfd8c`).
- **Plug-in trace log** is set to All in Dev, so each guard run is logged (`DealOS portal guard: …`). Set it back to Exception before go-live.

**Local development:** `PORTAL_URL=https://dealos-gigacore.powerappsportals.com npm run dev` proxies `/_api` to the site. Signed-in calls from localhost need the bearer-token setup in Microsoft's [code sites guide](https://learn.microsoft.com/power-pages/configure/create-code-sites). Until that is done, test on the deployed site.

## Test checklist (first sign-in)

Use a tenant account (gigacore or a teammate). Name test companies `[AGENT-TEST] …` so the clean-up script finds them.

1. Open the site and sign in. The catalog shows `Copper cathode (Grade A), LME Grade A, 300 MT` with no seller name.
2. **Company:** create `[AGENT-TEST] Portal Buyer Ltd` with role Buyer. The KYB status shows *In progress* within a minute (Party onboarding flow).
3. **Buying:** create an RFQ, send it, and open the listing from the catalog → *Invite seller to quote*.
4. **Assistant:** ask the Buyer Concierge for copper cathode. The reply appears in about 30 seconds.
5. **Security checks.** Run these in the browser console while signed in; each must fail with the guard's message:
   - `fetch('/_api/gc_listings(74b77e15-6dc1-f111-aaaf-7ced8daf451f)')` → 403 or empty (not your listing).
   - Create a listing, then PATCH its `gc_status` to `303300004` (Published) → *"A listing can only be submitted for verification or withdrawn from the site."*
   - PATCH your company's `gc_trusttier` → *"The field 'gc_trusttier' is managed by DealOS…"*

After a session, `python3 tools/dv.py get "plugintracelogs?\$select=messageblock,createdon&\$filter=contains(typename,'PortalGuard')&\$orderby=createdon desc&\$top=20"` shows what the guard saw.
